**"Zero-Shot, Few-Shot, or Retrieval-Augmented? Prompting Strategies for ICD-10 Coding with Open-Weight LLMs"*

## 0. Ground rules (non-negotiable)

1. **Numbers come only from code.** Nothing is hand-typed, estimated, rounded differently, or "expected". If a run cannot be performed (no GPU, no MIMIC access), say so; never fabricate or fill placeholders with plausible numbers.
2. **Mock results must never look real.** A `MockBackend` exists for CPU tests. Anything it writes goes to `results_mock/` and every row carries `"backend": "mock"`. `evaluate.py` must refuse to mix mock and real rows and must print a loud `MOCK DATA` banner for mock rows.
3. **One variable changes between arms: the evidence block** (nothing / 5 worked examples / retrieved candidates). System prompt, instruction, output format, record rendering, decoding params, seed, eval set, parser are identical across the three strategies. This is enforced by a test (see §10).
4. **Never tune prompts on the eval split.** Use the separate `dev` split for debugging prompts.
5. **No silent behaviour.** Every truncation, overflow, parse failure, skipped record, retrieval fallback is logged per instance and aggregated in evaluation.
6. **Write `ASSUMPTIONS.md` first** (see §12) and update it whenever you make a decision the paper does not specify.
7. **Real patient data (MIMIC-IV) never leaves the local machine**, is never committed, and never goes to an external API. Result files for MIMIC runs must not contain raw note text (store IDs, parsed codes, token counts only; raw model output only if it contains no copied note text, otherwise hash it).

## 1. What the paper claims (so you build the right thing)

- **Task:** for a clinical record R, predict the set of ICD-10-CM codes Y that a coder would assign (multi-label).
- **Models (2):** `meta-llama/Meta-Llama-3-8B-Instruct` (context 8192, gated on HuggingFace) and `BioMistral/BioMistral-7B` (context **2048**).
- **Strategies (3):** zero-shot; few-shot (k=5 worked examples, pool disjoint from eval set, checked at run time); RAG (embed all ICD-10-CM code descriptions, retrieve top-k by cosine similarity using multiple queries per record: the note text and each medication separately; model may pick from candidates, ignore them, or add its own code).
- **6 configurations** = 2 models × 3 strategies. 4-bit NF4 quantisation, **greedy decoding (temperature 0)**, fixed seed, same eval set.
- **Data:** a *synthetic* corpus generated by our own generator: free-text discharge-summary-style records; ~half of gold codes **implicit** (inferable only from medications/labs); negation distractors, family-history distractors, distractor medications; 3–6 comorbid conditions per record; long-tailed code frequency; every gold code validated against the official CDC/NCHS ICD-10-CM list, **generator refuses to emit a code not in the vocabulary**.
- **Metrics:** Micro-F1, Macro-F1 (gold-set variant), Precision@5, Precision@8 (only over instances with ≥k emitted codes, with the contributing count reported), **Invalid Code Rate** (share of emitted codes that do not exist in ICD-10-CM), **Unsupported Code Rate** (share of emitted codes that exist but are not in that record's gold set).
- **Phase 2 (journal extension) adds:** (a) paired bootstrap significance testing (B=10,000) on Micro-F1 and Macro-F1; (b) ablations of embedder, candidate pool size k, implicit-code rate; (c) validation on real de-identified MIMIC-IV discharge summaries; (d) operational metrics: prompt overflow rate, truncation rate, wall-clock per instance, GPU used.
- **Output files the paper references by name:** `src/evaluate.py`, `src/synth_data.py`, `src/run_experiment.py`, `src/data_prep.py`, directory `results/`. Keep exactly these names and paths.

Build **Phase 1 completely first**, get it green, then Phase 2.

## 4. Component specs

### 4.1 Vocabulary (`vocab.py`, `codes.py`)

- Source: CDC/NCHS ICD-10-CM files page (`https://www.cdc.gov/nchs/icd/icd-10-cm/files.html`). Pin **one fiscal-year release** in config and record its name + SHA-256 in `meta.json`. If the network is unavailable, accept a manually placed file in `data/raw/` and say exactly which file to download.
- Parse the "order"/code-descriptions file (fixed-width: order no., code, header-vs-billable flag, short description, long description). **Inspect the first lines and assert the column layout** before trusting it; fail loudly if it changes.
- Store per code: `code` (canonical dotted form, uppercase, e.g. `E11.9`), `is_billable`, `short_desc`, `long_desc`.
- `normalize(s)`: strip, uppercase, remove spaces, insert the dot after the 3rd character if missing (`E119` → `E11.9`). Format-only leniency, applied identically to every arm.
- Well-formed pattern: `^[A-TV-Z][0-9][0-9AB](\.[0-9A-TV-Z]{1,4})?$`.
- **Validity definition (decision to record in ASSUMPTIONS.md):** a code is *valid* iff it exists anywhere in the pinned CDC file (header or billable), matching the paper's "does not exist in ICD-10-CM". Also log, as a separate diagnostic, the **non-billable rate** (valid but header-level codes), because billing systems reject those too. Do not merge the two.
- Expose `Vocabulary.is_valid(code)`, `.description(code)`, `.all_codes()`.

### 4.2 Synthetic generator (`synth_data.py`)

CLI: `python src/synth_data.py --n-eval 200 --n-fewshot-pool 50 --n-dev 30 --implicit-rate 0.45 --seed 42 --out data/synthetic/<run_id>`
(`implicit_rate` must be a CLI parameter, the journal ablation sweeps {0.0, 0.25, 0.45, 0.65}.)

**Condition library** (`src/templates/*.yaml`), ≥ 60 conditions across cardiometabolic, respiratory, neuro, GI, renal, endocrine, psychiatric, musculoskeletal, infectious. Each condition entry:
```yaml
- code: "E11.9"
  explicit_phrases: ["type 2 diabetes mellitus", "T2DM", "diabetes mellitus type 2"]
  implicit_signals:
    medications: ["metformin 500 mg BID", "glipizide 5 mg daily"]
    labs: ["HbA1c 8.4%"]
  negation_phrases: ["no history of diabetes", "denies diabetes"]
  family_history_phrases: ["mother had type 2 diabetes"]
  distractor_meds: []        # meds that sound related but do NOT imply this code
  weight: 1.0                # base sampling weight (long tail applied on top)
```
Starter examples (the agent must verify **every** code against the real vocabulary and add more): `E11.9, I10, E78.5, J44.9, I48.91, E03.9, K21.9, J45.909, G47.33, I50.9, E66.9, D64.9, E55.9, M10.9, G40.909, I25.10, F41.9, N39.0, J18.9, I63.9`. Use **only unambiguous med→code or lab→code mappings** in `implicit_signals` (avoid e.g. "sertraline" because it maps to several codes); every implicit mapping must be defensible to a clinician.

**Per-record generation:**
1. Sample 3–6 conditions without replacement, using a Zipf-like weighting so code frequencies have a genuine long tail (not flat).
2. For each chosen condition, decide **explicit vs implicit** with probability `implicit_rate`. Explicit: name it in free text. Implicit: never name it; only a medication and/or lab appears.
3. Add 1–3 **distractors** per record from: negations ("no history of X"), family history, distractor medications. Distractor conditions must never enter the gold set. A distractor must not coincide with a gold condition in the same record.
4. Render as a discharge-summary-style note (Chief Complaint, HPI, Past Medical History, Hospital Course, Discharge Medications, Discharge Diagnosis-style free text *without* listing implicit conditions). Vary sentence templates and ordering so a model cannot key on a fixed layout.
5. Record fields (JSONL): `id, split, text, medications (list), gold_codes (list), implicit_codes (list), explicit_codes (list), distractors (list), n_words, seed`.
6. **Hard checks (refuse to run on failure):** every gold code is valid in the vocabulary; splits are disjoint by `id` **and** by text hash; implicit codes never appear by name/phrase in `text`; no gold code is also a distractor in the same record.
7. **Length constraint (important):** BioMistral's 2048-token limit applies to the *whole* prompt. A 5-shot prompt contains 6 records. Target a mean record length of roughly **120–220 words** (add `--max-words`) so that BioMistral few-shot does not overflow on synthetic data; the paper states the ceiling is "not binding" on the synthetic set. **Measure** overflow in the smoke test (§9). If overflow still occurs, **do not silently reduce k or alter the arms** — log it, report it, and tell the user (the options are: shorter records, or reporting the overflow honestly as a finding).

**`stats.json`** (the paper's §3.4 needs these exact items): number of records, unique gold codes, mean gold codes per record, mean record length (words), percentage of gold codes that are implicit, code-frequency histogram (also write a PNG/CSV).

### 4.3 Retrieval (`retrieval.py`)

- `build_index(embedder_name, vocab)`: embed the **long description** of each code as `"{code}: {long_desc}"` (decision to record; keep identical across embedders), batch encode, L2-normalise, save `.npy` + `codes.json` + `meta.json` (embedder name + revision, vocab hash, dim, date). Skip rebuild if `meta.json` matches.
- `Retriever.retrieve(record) -> list[Candidate(code, desc, score, source_query)]`:
  - **Queries per record:** the note text **and each medication separately** (as in the paper).
  - **Note-text caveat:** MiniLM silently truncates at ~256 word-pieces. Do not let that happen silently: split the note into overlapping windows (e.g. ~150 words, 30 overlap) and treat each window as a note query. Log this as a clarification in ASSUMPTIONS.md.
  - For each query take the top-m (m ≥ k) hits; merge across queries by **max score per code**; return the global top-k (default **k = 20**, configurable; ablation sweeps {10, 20, 30, 50}). De-duplicate codes. Restrict candidates to valid codes.
  - Use the embedder's recommended encoding mode (e.g. no instruction prefix for MiniLM; document if a different embedder needs one).
- Retrieval must never see gold labels. Log retrieved candidates per instance so retrieval can be audited.
- **Extra cheap diagnostic (label as "not in paper"):** candidate **recall@k of gold codes** (fraction of gold codes present in the candidate list) and mean candidates per record. This needs no LLM and explains RAG results.

### 4.4 Prompts (`prompts.py`)

Single-turn prompt: one user message in every arm (this avoids chat-template incompatibilities). Fixed text — do not reword per arm:

```
SYSTEM: You are an experienced clinical coder. You assign ICD-10-CM diagnosis codes to patient records.

USER:
Read the patient record and list every ICD-10-CM diagnosis code that a professional coder would assign. Include conditions that are not named but are clearly implied by the medications or lab values. Do not code conditions that are negated, belong to family members, or that the patient does not have. Respond with ONLY a JSON object of the form {"codes": ["<ICD-10-CM code>", ...]}, most important codes first, and nothing else.

{EVIDENCE_BLOCK}          <- the ONLY part that differs

PATIENT RECORD:
{record_text}

Medications: {med1}; {med2}; ...        <- identical rendering in all arms

ANSWER:
```

- **Zero-shot:** `EVIDENCE_BLOCK` absent entirely (not just empty — the rendered prompt minus the block must be byte-identical across arms; see test).
- **Few-shot:** `Worked examples:` then 5 examples, each `Record: ... / Medications: ... / Answer: {"codes": [...]}` in exactly the answer format above. The 5 shots are drawn from `fewshot_pool` **once** by seed (same 5 for every eval instance, stratified so ≥2 contain implicit codes), and at run time assert disjointness from eval by `id` and text hash. Persist the chosen shot IDs in `run_meta.json`.
- **RAG:** `Candidate ICD-10-CM codes retrieved for this record (you may use them, ignore them, or add another code the record clearly supports):` then one line per candidate `E11.9 — Type 2 diabetes mellitus without complications`. Do **not** force selection.
- Render through each model's own chat template (`tokenizer.apply_chat_template`). **Gotcha:** Mistral-style templates (BioMistral) reject a `system` role — in that case prepend the *same system text* to the user message. Record `template_mode` in the results. LLaMA-3 uses the real system role.

### 4.5 Backends (`backends.py`)

```python
class LLMBackend(ABC):
    def load(self) -> None: ...
    def count_tokens(self, messages) -> int: ...
    def generate(self, messages, max_new_tokens: int) -> GenResult: ...   # text, prompt_tokens, new_tokens, latency_s
    @property
    def info(self) -> dict: ...   # model_id, resolved revision sha, quantisation, dtype, device/GPU name, library versions
```
- `HFBackend`: NF4 as in §2; `do_sample=False`, no temperature/top_p; `max_new_tokens=256` (decision; identical for all arms); **batch size 1** by default (padding changes numerics → breaks determinism; allow `--batch-size` only with a documented warning); set `torch.manual_seed`, `numpy`, `random`, and `torch.use_deterministic_algorithms` where feasible. LLaMA-3 **stop tokens:** pass `eos_token_id=[tokenizer.eos_token_id, tokenizer.convert_tokens_to_ids("<|eot_id|>")]`. Strip the prompt from the decoded output (decode only new tokens). Resolve and log the exact model commit SHA (`huggingface_hub`), field name **`model_revision`** (the paper says `run_experiment.py` logs this).
- LLaMA-3 is gated: read `HF_TOKEN` from the environment; fail with a clear message explaining that the user must accept the Meta licence on the model page first.
- `MockBackend`: deterministic fake outputs (e.g. echoes a few gold-independent codes plus one invalid code) for CPU tests only.
- Free GPU memory between models (`del model; gc.collect(); torch.cuda.empty_cache()`). Load each model once and run all three strategies on it.

### 4.6 Output parser (`parser.py`) — identical for all arms

1. Try to parse the first JSON object containing a `"codes"` list. `parse_mode="json"`.
2. Fallback: regex-extract all well-formed code-like tokens from the output. `parse_mode="regex"`.
3. If nothing: `parse_mode="empty"`, codes `[]`.
4. `normalize()` every code, drop empty strings, **de-duplicate preserving order** (order matters for P@k).
5. Do **not** drop invalid codes here — they must survive to be counted by Invalid Code Rate. Do **not** repair or "snap" them to the nearest valid code.
6. Report per-config **parse-failure rate** (`regex` + `empty` share) in the supplementary table.

### 4.7 Context handling (needed for BioMistral 2048)

For every instance compute `prompt_tokens` with the model's tokenizer. Define:
- `overflow = (prompt_tokens + max_new_tokens > context_limit)` evaluated **before** any truncation.
- If overflow: apply the policy in config (`overflow_policy`, default `truncate_record`): for real notes first extract the clinically decisive sections (Discharge Diagnosis, Brief Hospital Course, Chief Complaint, History of Present Illness, Past Medical History; case-insensitive header regex); if it still does not fit, truncate the *record text* from the end to fit and set `truncated=True`. Never truncate the instruction, evidence block, or the answer slot. Never change k or the shots.
- Log `overflow`, `truncated`, `prompt_tokens` per instance; aggregate overflow rate and truncation rate per configuration. An overflowing instance still counts in `n` unless the policy is `skip` (then it is excluded and the excluded count is reported). Default policy keeps it.

## 5. Metrics (`metrics.py`) — pure functions, heavily unit-tested

Let `pred_i` be the ordered, de-duplicated predicted list and `gold_i` the gold set for instance *i*.

- **Micro-F1:** pool TP/FP/FN over all instances; F1 = 2TP / (2TP+FP+FN). Define F1 = 0 when the denominator is 0.
- **Macro-F1 (gold-set variant, per paper §6.3):** per-code F1 over the **set of codes that occur in the gold labels of the evaluated instances**, then the unweighted mean. State this in the table footnote automatically. (Predicted-but-never-gold codes do not add terms; they still hurt Micro-F1 and the rates.)
- **P@k (k ∈ {5, 8}):** for instances with ≥ k emitted codes, precision of the first k emitted codes; mean over those instances. Report the contributing count `n_p5`, `n_p8` next to it. If zero instances qualify print `n/a`, not 0.
- **Invalid Code Rate:** (emitted codes not valid in the vocabulary) / (total emitted codes), pooled over instances, after de-duplication within a record.
- **Unsupported Code Rate:** (emitted codes that are valid **and** not in that record's gold set) / (total emitted codes). Note that the two rates plus precision-like share sum to 1; add a test for that identity (invalid + unsupported + true-positive share = 1).
- Zero total emitted codes → rates are `n/a`, never a division error.
- Supplementary: mean codes emitted, parse-failure rate, overflow rate, truncation rate, mean/median latency per instance, GPU name, non-billable rate, and (RAG only) candidate recall@k.

`python src/run_experiment.py --config configs/phase1.yaml --models llama3 biomistral --strategies zero_shot few_shot rag --split eval --out results/<exp_id>`

- Deterministic order of instances (sorted by id). Progress bar with ETA. `--limit N` for smoke tests (results dir suffix `_smoke`).
- Do not auto-retry generation with different settings. One greedy generation per instance.

## 7. Evaluation (`evaluate.py`)

`python src/evaluate.py --results-dir results/<exp_id> --data data/synthetic/<run_id>/eval.jsonl [--format markdown|csv|json]`

- Joins results to gold **by id**; errors if any result id is missing from the dataset or any configuration has a different set of ids (override only with `--allow-partial`, which prints a warning banner listing the differing `n`s).
- Prints **Table II exactly in the paper's columns:** `Model | Strategy | n | Micro-F1 | Macro-F1 | P@5 | P@8 | Invalid Code Rate`, rows in the paper's order (LLaMA-3-8B zero-shot, few-shot (k=5), RAG; BioMistral-7B same). Fixed formatting: F1/P as 3 decimals, rates as percent with 1 decimal. The same formatting is used everywhere; no manual rounding.
- Then prints **Table S1** (supplementary): Unsupported Code Rate, parse-failure rate, overflow rate, truncation rate, mean codes emitted, `n_p5`, `n_p8`, mean latency, GPU, RAG candidate recall@k.
- `--dump-invalid N`: prints up to N verbatim invalid code strings with the configuration and record id (the paper wants 2–5 verbatim hallucinated examples).
- Also writes `reports/table2.md`, `.csv`, `.json` (machine-readable, includes the exact config hash and result-file SHA-256s so a paper number can be traced back to files).
- Sanity checks it must run: gold-as-prediction gives Micro-F1 = Macro-F1 = 1.0, Invalid = Unsupported = 0; empty predictions give F1 = 0 (covered in tests).
- **Reference baselines (extras, label "not in paper"):** (a) majority-code baseline (always predict the N most frequent train-pool codes), (b) retrieval-only baseline (top-5 retrieved candidates, no LLM). They give the reader a floor to interpret the LLM numbers.

## 8. Phase 2 components

### 8.1 Significance (`significance.py`)
- Input: the six per-instance result files + gold. Paired bootstrap, **B = 10,000**, seeded, resampling **instance ids with replacement, the same resample indices for both configurations being compared**.
- Efficient implementation: precompute per-instance TP/FP/FN contributions (sparse instance×code matrices); a resample is a vector of multiplicity counts, so metrics are matrix products, no Python loops over 10k × n.
- For each model: Δ for **(RAG − zero-shot), (RAG − few-shot), (few-shot − zero-shot)**, on **Micro-F1 and Macro-F1** (macro recomputed over the gold-code set of each resample). Also, per strategy, the model effect (LLaMA-3 − BioMistral).
- Report point Δ, mean bootstrap Δ, 95% percentile CI, and whether the CI excludes 0. Print **all** comparisons, including non-significant ones. Output `reports/significance.md/.csv`.

### 8.2 Ablations (`ablations.py` + configs) — use the best model from Table II to stay affordable
- **Embedder:** `all-MiniLM-L6-v2` vs a biomedical encoder (`pritamdeka/S-PubMedBert-MS-MARCO`); k and corpus fixed.
- **k:** {10, 20, 30, 50}; embedder and corpus fixed.
- **Implicit rate:** regenerate the corpus at {0.0, 0.25, 0.45, 0.65} with identical seed and other params, run **zero-shot and RAG** at each level to test whether the RAG advantage grows with implicit rate.
- Each ablation writes to its own results subdirectory, is evaluated by `evaluate.py`, and yields its own small table: `variant | Micro-F1 | Macro-F1 | Invalid Code Rate | Overflow Rate` (+ candidate recall@k for the k-sweep). Check prompt length for k=50 on BioMistral (overflow likely) and report it rather than hide it.

### 8.3 MIMIC-IV validation (`data_prep.py`) — only after PhysioNet credentialed access
- Inputs (local paths via config): MIMIC-IV-Note `discharge` table and MIMIC-IV `diagnoses_icd`.
- Keep admissions whose diagnoses are **`icd_version == 10`** only. Convert MIMIC's undotted codes (`E119`) to canonical dotted form via `normalize()`.
- Draw a held-out random sample (config: `n`, `seed`); record the filter counts at each step (the paper must report "exactly what filtering we applied").
- Extract sections per §4.7 (case-insensitive headers). Warn in the log that "Discharge Diagnosis" text can sit very close to the label — this is the paper's design, keep it, and mention in ASSUMPTIONS.md.
- Report the fraction of gold codes **not present in the pinned vocabulary version** (MIMIC spans several code-set years). Default: keep them (they count as misses) and report the fraction.
- Few-shot pool for MIMIC: either the synthetic pool (default, labelled as such) or a disjoint MIMIC sample; make it a config choice and record it.
- Run the same six configurations with the same code, same prompts, same parser, and evaluate side by side with the synthetic numbers. **Privacy guards:** data under a gitignored path; no raw note text in result files; refuse to run if the configured output directory is inside a git-tracked path; check the PhysioNet data-use agreement before using any hosted notebook or cloud GPU (default: local or institutional machine only).
- If MIMIC access is not available, skip this step cleanly with a message; never create stand-in "real" numbers.

## 10. Tests (`tests/`, run with `pytest`, must pass on CPU without downloading big models)

1. **Prompt invariance:** for the same record, render zero-shot, few-shot and RAG prompts; remove the evidence block; assert the three remainders are **byte-identical**. Also assert the system text and instruction strings are the same objects/values.
2. **Few-shot disjointness:** a pool that overlaps eval (by id or text hash) raises an error.
3. **Metrics on hand-computed fixtures:** micro/macro-F1, P@k with the `n_pk` counts, rates, empty-prediction, zero-denominator cases, the identity invalid + unsupported + TP-share = 1. Cross-check micro-F1 and per-code F1 against `scikit-learn` in the test only.
4. **Parser:** JSON happy path, JSON with prose around it, malformed JSON → regex fallback, empty, lower-case codes, undotted codes (`E119`), duplicates (order preserved), invalid codes preserved (e.g. `Z99.999` or `E11.99`).
5. **Vocab:** known valid/invalid codes; `normalize()` round trips; layout assertion triggers on a corrupted line.
6. **Generator:** with a fixed seed, output is byte-identical across two runs; every gold code valid; implicit codes' names absent from text; distractors never in gold; splits disjoint; implicit-rate within tolerance on a large sample; the generator **raises** when a template contains an invalid code (use a fixture with a bad code).
7. **Retrieval:** on a tiny fake vocabulary and a deterministic fake embedder: max-score merge across queries, top-k size, determinism, no duplicates.
8. **Resume:** simulate a crash mid-run with the mock backend; the restart completes with no duplicates and no lost lines.
9. **Bootstrap:** with identical predictions Δ = 0 and CI ⊂ tiny interval around 0; with a constructed clearly-better system the CI excludes 0; same seed → same CI.
10. **Overflow logic:** a synthetic long record on a mock 2048-limit tokenizer sets `overflow`/`truncated` correctly and never cuts the instruction or evidence.
11. **Mixing guard:** `evaluate.py` refuses a directory mixing mock and real rows.

## 11. Reliability and reuse requirements

- Every random choice flows from the config `seed` (record the seed in each output row). Same inputs + same code ⇒ same dataset, same shots, same retrieval, same outputs (up to GPU numerics, noted in README).
- Everything configurable lives in YAML (models, HF IDs, revisions, context limits, `max_new_tokens`, k, embedder, paths, seed, overflow policy); no magic constants in code. Adding a third model or strategy must need only a config entry (+ one small class for a new strategy).
- Strategies are small classes implementing `build_evidence(record) -> str | None`; models are `LLMBackend` instances. The harness, parser, and evaluator know nothing about which strategy produced a row.
- Type hints, docstrings on public functions, `logging` (not `print`) except for the evaluator's tables, atomic file writes, clear error messages with remediation ("accept the Llama-3 licence at …", "set HF_TOKEN", "no CUDA GPU found: use --backend mock for tests only").
- `README.md` has copy-paste commands for: setup → vocab → data → index → smoke → phase1 → evaluate → significance → ablations → tests, and a "what each number in the paper maps to" table (Table II ↔ `evaluate.py` main table; §4.3 examples ↔ `--dump-invalid`; §4.4 ↔ Table S1; §4.5 ↔ MIMIC run; §4.6 ↔ ablation tables; §4.7 ↔ `significance.py`).
